# Pipeline variants as data — one Identity Spec per family, one file per variant

## Status

**Canon.**

The motion-primitives library would inflate the Pipeline registry from ~22 entries to ~40 if every motion variant landed as its own Pipeline registration. The cost is not the registry line — that part is cheap — it is the duplication structure that comes with it: each new Pipeline re-declares its Identity Spec, copies the family's CanvasSource, owns a separate path in `PIPELINE_REGISTRY`, and forces every Brief / brainstorm / Critic step to discriminate between Pipelines that share their entire Identity Spec and differ only in motion shape. The duplication pulls the engine the wrong way: ADR-0015 says an Identity Spec is the dimensions of the claim; if `instance-stack-vertical` and `instance-stack-horizontal` make the same claim (text slot rendered as N spatially-offset instances with per-instance progress lag) and differ only in the *shape* of the offset, the engine should encode them as one claim with two motion shapes, not two claims that happen to be similar. ADR-0014's Pack/Preset split assumes a Preset names a Pipeline by id and a Pack resolves the Pipeline's `viaPack` Roles; one Pipeline-per-variant means a Pack has to enumerate fill/edge/depth/light Roles for `instance-stack-vertical` and again for `instance-stack-horizontal` and again for every future variant, and the Pack manifest grows linearly with variant count for no semantic gain. We pin a layer-agnostic convention: a Pipeline that hosts a *family* of motion shapes carries a `variants/` subfolder; each variant is a single file declaring `{ id, label, defaults, motionShape }`; the family's `index.ts` builds a Zod discriminator from the `VARIANT_IDS` array and dispatches to the active variant's `motionShape` function at render time; the family declares one Identity Spec that every variant must implement. Adding a new variant is one file in `variants/` and one line in `variants/index.ts`; no Pipeline registration entry, no Identity Spec re-declaration, no Pack manifest delta. The convention applies wherever a true family exists — Surface, Block, Overlay, and Annotation are all eligible — and explicitly *does not* apply to single-shape Pipelines that ship with only one motion (`cursor-trail`, single-shape Effects).

## Considered options

One Pipeline per variant with no families (rejected: the duplication argument above — Identity Spec re-declaration per variant, Pack manifest growth linear in variant count, brainstorm discrimination between Pipelines that share their claim, and the structural pull toward "add a new Pipeline for any new motion idea" that the motion-primitives plan specifically called out as the cause of library narrowness). Family Pipelines with variant strings interpreted by a runtime switch inside the family's render path (rejected: collapses to the same shape mechanically but loses the per-variant file boundary — the family's render code grows linearly in variant count, the diff for "add a variant" touches the family's core file, and a new variant cannot ship without editing code that other variants depend on; the `variants/` folder boundary is what makes the next variant a one-file change). Variants as Pack manifest entries instead of Pipeline files (rejected: a variant *is* a motion shape, which is structurally a Pipeline concern under ADR-0015 — the motion-form dimension is what differentiates the variants and motion-form dimensions are intrinsic to the Pipeline, not Pack-resolved; conflating "variant" with "Pack Role" puts motion-form on the wrong side of ADR-0019's via-pack boundary). Per-variant Identity Specs sharing a parent (rejected: an Identity Spec inheritance hierarchy adds a kind dimension to the type system without giving anything the single-Spec-per-family shape doesn't give — the family-level Spec already names every dimension every variant must implement, and a variant that cannot implement one of the family's dimensions is not a variant, it is a new Pipeline). Allow a variant to opt out of one of its family's dimensions (rejected: collapses ADR-0015's gate exactly where the variants pattern would otherwise be abused — "this variant doesn't really do depth-treatment, mark that dimension as not-applicable" is the structural definition of shipping a div under the family banner). Variant id as a free-form string at the Preset level (rejected: a variant id is part of the Pipeline's surface area — adding a variant widens the Zod enum the Preset schema validates against, and the export to `docs/preset-format.schema.json` must regenerate; an unguarded string skips that regeneration and lets Presets reference variants that no longer exist).

## Consequences

A family Pipeline's folder gains the shape:

```
src/lib/pipelines/<layer>/<family>/
  index.ts               # Exports <concept><Layer>Renderer; builds schema from VARIANT_IDS
  identity.ts            # one Identity Spec for the family
  CanvasSource.svelte    # one render path; reads active variant by id
  variants/
    types.ts             # <Family>Variant interface
    index.ts             # VARIANTS record + VARIANT_IDS array
    <variant-a>.ts       # one file per variant
    <variant-b>.ts
```

The variant file is a pure data record plus a deterministic motion function: `{ id: string; label: string; defaults: Record<string, unknown>; motionShape: (i: number, n: number, progress: number) => MotionState }`. Motion functions are pure — no reads of `engineState`, no DOM access, no `Date.now()`, no `Math.random()`. The constraint is enforced by code inspection in the Critic and by the registration validator refusing variant motion functions that import from `$lib/platform/engine-state.svelte` or from any module under `src/lib/platform/`. Every shipped variant must implement every Identity Spec dimension the family declares; a variant that cannot is rejected at registration time as the family's Identity Spec walks against the active variant's actual rendered output. The default variant is always the most restrained option of the set — the unanimated frame already needs to read as finished composition per the binding rule "defaults look good at progress=1," and the lowest-novelty variant is the safest default; louder variants ship as explicit Producer picks. Variant id is part of the Preset schema: the Pipeline's `index.ts` exports a Zod discriminator built from `VARIANT_IDS as [string, ...string[]]`, the schema export script regenerates `docs/preset-format.schema.json` whenever variants change, and Preset validation rejects unknown variant ids. The lower-third migration in Phase 2.1 is the worked example: `src/lib/pipelines/overlays/cinematic-lower-third/` collapses into `src/lib/pipelines/overlays/lower-third/variants/cinematic.ts` alongside the existing chip-shape as `variants/standard.ts`; the family's one Identity Spec covers both; the two Preset files migrate from `{ type: 'lower-third' }` and `{ type: 'cinematic-lower-third' }` to `{ type: 'lower-third', variant: 'standard' | 'cinematic' }`. Adding a third variant later (e.g. `card-stacked`) is one file in `variants/` + one line in `variants/index.ts` + schema regen — no edits to `Workspace.svelte`, no edits to `PIPELINE_REGISTRY`, no new Identity Spec. The convention is layer-agnostic but the *trigger* is family-shape, not layer-shape: a Surface family like `type-hero` migrating from single-shape to `variants/single.ts` + `variants/pair.ts` (Phase 4.1) follows the same convention as the Block-layer `instance-stack` (Phase 4.2). Single-shape Pipelines (`cursor-trail`, `depth-of-field`, `card-pair`) do not get a `variants/` folder — the pattern is for families, and a single-shape Pipeline that later grows a variant adopts the pattern by adding the folder and migrating its existing shape into a variant file in the same diff. The Pack manifest grows by zero Roles per variant — every variant inherits its family's `viaPack` declarations from the single Identity Spec, which is the structural property that makes the variants pattern cheap for Packs and the reason ADR-0019's via-pack clause was the prerequisite for this ADR.
