# Time-driven `EffectPackContext` for the per-layer effect chain

`EffectPassDefinition.pack(params)` (introduced alongside the per-layer effect chain in `src/lib/platform/pipelines/types.ts` and consumed by `EffectChain` in `src/lib/platform/pipelines/effect-chain.ts`) saw only the effect's static `params` — the timeline-driven scrub state was not threaded in, so any imported shader that wanted to animate from a `u_time` / `u_progress` uniform (the calling convention used by every time-driven shader on shaders.com, ShaderToy, and most WebGPU/WGSL galleries) had nowhere to read it. We resolved this by widening `pack` to `pack(params, ctx: EffectPackContext)`, where `EffectPackContext = { progress: number; timestamp: number }`, and plumbing both values from the timeline scrub through `EffectChain.apply()` → the internal compiled-effect closure → each effect's `pack`. Both call sites in `Workspace.svelte` (the live `renderAt` path and the export `renderFrame` path) compute the same `{ progress, timestamp }` pair from the active scrub via a shared `effectChainTimebase(timestamp)` helper, so preview and export agree at every frame. Time-driven effects now declare a `progress: d.f32` (or `timestamp: d.f32`) field in their `paramsStruct`, write `ctx.progress` (or `ctx.timestamp`) into that field inside `pack`, and reference `layout.$.uniforms.progress` in WGSL — the same shape every other uniform takes.

## Considered options

- **Pass only `progress`** (rejected: most shaders.com / ShaderToy ports expect a `u_time` in seconds, not a normalized 0..1 ramp. Forcing every author to multiply `progress * durationSeconds` inside WGSL — and remember to update it if the transport duration ever flows in as a uniform — buys nothing. Both values derive from the same `timestamp / durationSeconds` division and cost one extra `f32` to forward).
- **Pass only `timestamp`** (rejected: rubric language and `timeline.svelte.ts` are progress-first — animation timings in `MarkTiming` / `Transition` are all expressed as fractions. A `progress`-native uniform is the easier port for any shader written against the Hiviz vocabulary, even though `timestamp` is the easier port for the wider shader ecosystem. Both is cheap; biasing the contract either way is unnecessary friction).
- **Reuse `ShaderPass<T>.packUniforms(target, bounds)` for the effect chain** (rejected: `ShaderPass` is keyed to a per-target content shape (`SurfaceState` for surfaces, `overlay.content` for overlays per ADR-0010); effects are layer-level passes whose only target is their own `params`, with no surface/overlay bounds to pack. Folding the two would force every effect's `pack` to take a meaningless `bounds` argument and force every shader pass to take a meaningless `progress`. Two thin context shapes are clearer than one bloated one).
- **Read `timeline.time` from inside `EffectChain.apply` instead of threading it as an argument** (rejected: the chain runs on both the live preview path and the export path, and the export path drives `renderFrame(frame, timestamp)` from a paused-by-progress export loop that never touches the live `Timeline` instance. Reading shared state would silently desync the two paths — exactly the frame-determinism failure mode the contract exists to prevent. Threading the value the caller already has is the only path that keeps preview and export pixel-identical).
- **Defer the wiring until a real time-driven effect lands** (rejected: every shaders.com import past the spatial-only minority needs this wiring. Adding it now unblocks the entire animated category for a five-line engine change and one `_ctx` arg in the existing spatial-only effects (`paper-grain`, `chromatic-aberration`)).

## Consequences

Time-driven effects port one-to-one from shaders.com / ShaderToy: declare a `progress` (or `timestamp`) field in `paramsStruct`, write `ctx.progress` into it inside `pack`, and reference `layout.$.uniforms.progress` in WGSL — the same shape every other uniform takes. The transparency contract holds: `pack` only writes uniforms; the chain's `loadOp: 'clear'` with `[0, 0, 0, 0]` is unchanged. The frame-determinism contract holds and is in fact tightened: every effect now reads the same scrub value the surface render reads, sourced from one `effectChainTimebase` helper in `Workspace.svelte` so the live and export paths cannot drift. Existing spatial-only effects (`paper-grain`, `chromatic-aberration`) absorb the signature widening with `_ctx` in `pack` and behave identically to before. The Critic protocol (docs/critic.md) does not need new gates — E4 (alpha preservation) and the frame-determinism rubric already cover the failure modes the new uniform could introduce. The next consumer is whichever Preset first imports a time-driven shader (gradient flow, animated noise, distortion fields); no further engine work is required at that point.
