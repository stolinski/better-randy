# @club_aqua_back_deck/dex-software-factory

Generate a reusable Swamp Software Factory lifecycle that uses Dex as its task ledger.

## What are Dex and Software Factory?

[Dex](https://github.com/zeeg/dex) is a repository-local task tracker for humans and coding agents. It gives each unit of work a stable ID, lifecycle state, result, relationships, and optional commit.

[`@swamp/software-factory`](https://github.com/swamp-club/swamp-extensions) is a model-driven state machine for running repeatable software-delivery stages. It enforces transitions and evidence gates, but it intentionally does not prescribe a specific lifecycle.

This extension connects those concepts by compiling consumer configuration into a portable Factory profile. The generated Factory performs bounded implementation and verification work, then completes the originating Dex task through a named `dex-task-tracker` model.

```text
Dex task
   ↓ work item
Software Factory lifecycle
   ↓ verified terminal result
Dex task-tracker completion
```

## What this package owns

The compiler generates this lifecycle:

```text
preflight → implementation → classify → verification
          → optional review or human approval
          → reconciliation → postflight
          → optional task-specific completion approval → Dex completion
```

It owns stage structure, base artifact contracts, transition routing, terminal ordering, and cycle limits.

You supply the repository-specific parts:

- Preflight, classification, verification, and postflight adapters.
- Prompts and execution budgets.
- Additional artifact fields.
- Optional review skills and acceptance approval policy.
- An optional distinct `completionGate` that parks after postflight and delegates closure to a repository-owned `completionWorkflow`.
- The name of the Dex tracker model to complete work through.

The package is a **profile compiler**, not another Factory engine. It does not contain project commands, local paths, credentials, or one repository's review conventions.

## Install

Pulling this extension also resolves its pinned `@swamp/software-factory` and `dex-task-tracker` dependencies:

```sh
swamp extension pull @club_aqua_back_deck/dex-software-factory
```

Create the tracker and profile compiler through Swamp:

```sh
swamp model create @club_aqua_back_deck/dex-task-tracker project-dex-tracker \
  --global-arg ownerToken=project-factory --json
swamp model create @club_aqua_back_deck/dex-software-factory \
  project-delivery-profile --json
```

Use `swamp model edit project-delivery-profile` in an interactive terminal and copy the `globalArguments` mapping from [`examples/profile-arguments.yaml`](examples/profile-arguments.yaml). Replace every example adapter name and prompt with consumer-owned configuration. Never copy or invent a model ID.

## Compile the profile

```sh
swamp model validate project-delivery-profile --json
swamp model method run project-delivery-profile compile
swamp data get project-delivery-profile compiled-profile --json
```

The `compiled-profile` resource contains:

- `compilerVersion` — compiler contract version.
- `target.type` and `target.version` — pinned Factory compatibility target.
- `factoryArguments.stages` — generated lifecycle stages.
- `factoryArguments.globalTransitions` — generated global routing.

Compilation is deterministic and does not execute any configured adapter.

## Create the generated Factory

Create the target definition, then bind its `globalArguments` to the compiled resource:

```yaml
globalArguments: '${{ data.latest("project-delivery-profile", "compiled-profile").attributes.factoryArguments }}'
```

```sh
swamp model create @swamp/software-factory project-delivery --json
swamp model validate project-delivery --json
swamp model method run project-delivery validate
```

The exact definition-editing mechanism is consumer-owned. Preserve the ID generated by `swamp model create`.

## Safety and portability boundaries

- Adapter inputs are declared with JSON-schema-shaped contracts.
- `workItem` remains compiler-owned and cannot be overridden.
- Contract extensions may add fields but cannot replace required base fields.
- Optional review, acceptance, and completion gates may be omitted.
- Optional `adapters.terminalObserver.workflow` routes done and aborted outcomes through required observability stages before their terminal states; the workflow owns the final `finalize` transition and non-gating telemetry.
- When `completionGate` is configured, rejection returns to implementation and `adapters.dexTracker.completionWorkflow` is required. That workflow must read authoritative Factory evidence and own the tracker mutation.
- Workflow and model names are configuration, not embedded project policy.
- No credentials are accepted or emitted.

See [`examples/usage.md`](examples/usage.md) for clean-repository validation. The accompanying `profile-arguments.yaml` is a configuration fragment, not a model definition.
